# Architecture

HogwartsRP has three independent pieces: Core owns authoritative server behavior and sessions, the Lua runtime executes resource scripts in separate worker processes, and the launcher selects servers and starts the game. The server's WebSocket adapter is transport code in the server host; Core and Lua resources depend on contracts rather than a game-specific client. There is still no Hogwarts Legacy multiplayer adapter, so the WebSocket path is usable by protocol clients but is not connected to the game.

The server discovers resource folders, parses the restricted manifest grammar without executing manifests, sorts dependencies deterministically, and starts one Lua worker process and state per resource. Server/shared scripts within a resource share that resource's state. Resource script paths are constrained to their resource folder. Core framework assemblies are never reloaded.

## Runtime status

The scripting host uses NLua 1.7.9 with KeraLua's Lua 5.4 native runtime (MIT licensed). Each resource runs in its own worker process. The host removes OS, IO, package, debug, coroutine, CLR bridge, dynamic loader, and protected-call globals before resource code runs, then installs an instruction-count hook. On Windows, a Job Object applies a hard per-worker private-memory limit and CPU-rate cap. On Linux, the worker applies `RLIMIT_DATA` and a per-request `RLIMIT_CPU`; the parent also enforces a wall-clock timeout and monitors private memory on both platforms. The worker still runs as the same OS user. No OS sandbox, restricted token, filesystem ACL, or network namespace is configured. Scripts have no file or network APIs exposed, but a runtime vulnerability could still execute with the worker user's permissions; treat resources as trusted.

Resource-local events stay inside the worker. Command registration is relayed to the server and invocations route back to the owning worker. The Core networking policy records client events explicitly registered by Lua resources; accepted messages carry the server-created player session ID and authenticated display name into the owning resource workers. Server resources can send events to authenticated sessions through the transport contract.

## Persistence

Character submissions are validated by `CharacterSubmissionService`, which derives ownership from the authenticated player session. The server project provides `JsonCharacterRepository` as a simple single-process implementation of `ICharacterRepository`. It loads records from a JSON file, serializes writes within its process, and replaces the data file through a same-directory temporary file. It rejects duplicate IDs and can retrieve records by owner. Corrupt JSON is surfaced as an error rather than silently resetting the store.

This is a persistence adapter only. The current server does not expose a character-submission endpoint or register the repository in a running request pipeline. Multi-process deployments, shared storage, backups, and encryption at rest require a stronger persistence solution.

## Security and actual game integration

Permission checks default to deny. WebSocket clients must present a single-use, short-lived join ticket. Tickets are stored as hashes, consumed once, and never establish permission claims. When configured, the server accepts an OIDC ID token only after validating its RS256 signature, issuer, audience, time claims, and a one-use server nonce; it then derives account identity from the signed issuer and subject. The `issue-ticket` operator command is disabled for non-loopback listeners. Remote listeners require HTTPS, while the default HTTP listener binds to loopback. Client events must be registered by a server resource and carry only bounded primitive JSON values. Clients cannot grant permissions or choose their server-owned session ID. Game character/house and character persistence interfaces are contracts only, and return unavailable until a real adapter is supplied. No game files, platform authentication, anti-cheat, or DRM are accessed or bypassed.

The launcher is separated behind installation detection, platform launch, credential-provider, network-client, and character-creation bridge interfaces. Its preview connects to the selected server using the shared WebSocket protocol and keeps that launcher-owned session alive while open. The optional OIDC provider uses the system browser, authorization code with PKCE, a loopback callback, and a nonce supplied by the selected server. The server validates the ID token and exchanges it for a one-use WebSocket ticket. The console ticket prompt remains for loopback development. The Windows detector checks conventional install roots plus caller-provided roots. The Steam adapter asks Steam to run app 990080 so ownership and authentication stay with the platform. Epic launch is not wired because no documented platform launch contract is included. Official mod support documents content creation and in-game mod management, but no direct character-creation launch API was found. The bridge therefore falls back to normal startup. Character submissions are validated on the server, with ownership derived from the authenticated session. The game itself is not attached to the launcher network session.

## Authenticated character submission

The WebSocket transport accepts a `submit_character` message only after the connection has authenticated and received a server-owned session. The server ignores any client-supplied owner field (the submission schema has none) and passes the authenticated account ID from that session into `CharacterSubmissionService`. The response is a `character_submission_result` message containing the request ID and the validated result. Submission payloads remain subject to the existing 32 KiB WebSocket frame limit and server-side field validation.

The server host constructs `JsonCharacterRepository` at startup. Configure `Storage:CharactersPath` to select a writable JSON file; the default is `data/characters.json` under the application base directory. This endpoint provides authenticated persistence over the launcher/server protocol only. It does not create or modify a character inside Hogwarts Legacy, and no game-client multiplayer adapter is implied.
