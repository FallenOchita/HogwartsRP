# Architecture

HogwartsRP has three independent pieces: Core owns authoritative server behavior and sessions, the Lua runtime executes resource scripts in separate worker processes, and the launcher selects servers and starts the game. The server's WebSocket adapter is transport code in the server host; Core and Lua resources depend on contracts rather than a game-specific client. There is still no Hogwarts Legacy multiplayer adapter, so the WebSocket path is usable by protocol clients but is not connected to the game.

The server discovers resource folders, parses the restricted manifest grammar without executing manifests, sorts dependencies deterministically, and starts one Lua worker process and state per resource. Server/shared scripts within a resource share that resource's state. Resource script paths are constrained to their resource folder. Core framework assemblies are never reloaded.

## Runtime status

The scripting host uses NLua 1.7.9 with KeraLua's Lua 5.4 native runtime (MIT licensed). Each resource runs in its own worker process. The host removes OS, IO, package, debug, coroutine, CLR bridge, dynamic loader, and protected-call globals before resource code runs, then installs an instruction-count hook. On Windows, a Job Object applies a hard per-worker private-memory limit and CPU-rate cap. On Linux, the worker applies `RLIMIT_DATA` and a per-request `RLIMIT_CPU`; the parent also enforces a wall-clock timeout and monitors private memory on both platforms. The worker still runs as the same OS user. No OS sandbox, restricted token, filesystem ACL, or network namespace is configured. Scripts have no file or network APIs exposed, but a runtime vulnerability could still execute with the worker user's permissions; treat resources as trusted.

Resource-local events stay inside the worker. Command registration is relayed to the server and invocations route back to the owning worker. The Core networking policy records client events explicitly registered by Lua resources; accepted messages carry the server-created player session ID and authenticated display name into the owning resource workers. Server resources can send events to authenticated sessions through the transport contract.

## Security and actual game integration

Permission checks default to deny. WebSocket clients must present a single-use, short-lived join ticket issued for an identity already trusted by the host. Tickets are stored as hashes, consumed once, and never establish permission claims. The current `issue-ticket` console command is an operator bootstrap for protocol development, not an account identity provider; connect a trusted authentication service before public deployment. Remote listeners require HTTPS, while the default HTTP listener binds to loopback. Client events must be registered by a server resource and carry only bounded primitive JSON values. Clients cannot grant permissions or choose their server-owned session ID. Game character/house and character persistence interfaces are contracts only, and return unavailable until a real adapter is supplied. No game files, platform authentication, anti-cheat, or DRM are accessed or bypassed.

The launcher is separated behind installation detection, platform launch, and character creation bridge interfaces. Its Windows detector checks conventional install roots plus caller-provided roots. The Steam adapter asks Steam to run app 990080 so ownership and authentication stay with the platform. Epic launch is not wired because no documented platform launch contract is included. Official mod support documents content creation and in-game mod management, but no direct character-creation launch API was found. The bridge therefore falls back to normal startup. Character submissions are validated on the server, with ownership derived from the authenticated session.
